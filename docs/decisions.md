# Решения, принятые при реализации стенда

ТЗ (docs/stand/grpc-stand-TZ.md) разрешает решать неоднозначности самым простым способом и записывать решение сюда.

## 1. Корень стенда = корень репозитория

В ТЗ структура описана от каталога `grpc-stand/`. В репозитории нет ничего, кроме стенда, поэтому лишний уровень вложенности не нужен: `Makefile`, `pyproject.toml`, `docker-compose.yml` и остальное лежат прямо в корне. Имя `grpc-stand` осталось у корневого проекта uv и у compose-проекта (`name: grpc-stand`).

## 2. Workspace и версия Python

- Корневой проект `grpc-stand` — виртуальный (`[tool.uv] package = false`), он только держит общие настройки ruff/mypy/pytest и dev-группу.
- Участники workspace: `packages/*` (stand_core) и `services/*`.
- `.python-version` = 3.12 — минимальная поддерживаемая версия, на ней идёт локальная разработка. Проверка на 3.14 — в отдельном venv, чтобы не пересоздавать `.venv`: `UV_PROJECT_ENVIRONMENT=/tmp/stand-venv-314 PYTHON=3.14.2 make install check test` (подробности — §18). `PYTHON` Makefile передаёт и в `uv sync --python`, и в `uv run --python`; `install` нужен, потому что корневой проект зависит только от `stand-core` и `stand-protos`, а пакеты сервисов ставит `uv sync --all-packages`.

## 3. Тесты и smoke

- `make test` запускает pytest с `-m 'not stand'` (задано в `addopts`), т.е. без smoke-сценария.
- `make smoke` запускает только тесты с маркером `stand` против поднятого `make up` стенда.
- pytest работает в `--import-mode=importlib`, чтобы одинаковые имена тестовых модулей в разных сервисах не конфликтовали.

## 4. Docker

- Один образ на все Python-сервисы: в рантайм-стадию копируется venv со всеми пакетами workspace (`uv sync --no-dev --all-packages --no-editable`). Сервис выбирается командой в compose. Так проще и образ собирается один раз; цена — в каждом контейнере лежит код соседей, на память это не влияет.
- `make up` = `docker compose up -d --build --wait`: `--build` добавлен, чтобы после правок кода не забывать пересобрать образ.
- Redis запущен без персистентности (`--save ''`, `--appendonly no`) и с `maxmemory 48mb` под `mem_limit: 64m`: данные стенда временные, `make reset` и так их сбрасывает.

## 5. mypy

`make typecheck` передаёт mypy только существующие каталоги из `packages services tests`, чтобы цель работала на любом этапе разработки. `gen/` исключён.

## 6. Proto-контракты и gen/

- Стиль — buf STANDARD: у каждого RPC свои `<Method>Request` / `<Method>Response` (даже `GetProduct` возвращает `GetProductResponse{product}`, а стримы — `ExportProductsResponse{product}`), значения enum с префиксом типа и нулевым `*_UNSPECIFIED` (`ORDER_STATUS_DELIVERED`, `USER_ROLE_SELLER`). Так контракт сразу проходит `buf lint`, а в уроках про `buf breaking` ломается только то, что сломано намеренно.
- `common.v1.Pagination{page_size, page_token}` вкладывается в списочные запросы полем `pagination`; `next_page_token` лежит прямо в ответе.
- Отчёт об импорте (`ImportReport` в ТЗ) — это сам `ImportProductsResponse` с полями `created`, `updated`, `failed`, `errors`, без лишней обёртки.
- catalog.v2: `Product.price` (`common.v1.Money`) — поле 10, номер 6 (`price_kopecks` в v1) свободен и **не** `reserved`. Фильтры цены в v2 — `Money min_price/max_price` (8, 9), номера 3 и 4 из v1 не используются. `region_id` — поле 7; обязательность проверяет сервер (в proto3 нет required).
- `gen/` — отдельный участник workspace `stand-protos` (`gen/pyproject.toml`), верхнеуровневые пакеты совпадают с каталогами protos: `common`, `users`, `catalog`, `orders`, `support`. Импорт: `from catalog.v1 import catalog_pb2`. `make gen` пересоздаёт только эти каталоги, `gen/pyproject.toml` не трогает, и докладывает `__init__.py` и `py.typed`.
- `.pyi` генерирует mypy-protobuf (`--mypy_out`, `--mypy_grpc_out`), а не `--pyi_out` protoc: оба пишут в один и тот же `*_pb2.pyi`, а стабы mypy-protobuf полнее (типизированные enum, oneof, gRPC-стабы для grpc.aio). Для mypy в dev-группе `types-grpcio` и `types-protobuf`.
- Нижние границы `grpcio` и `protobuf` в `stand-protos` равны версиям генератора: сгенерированный код проверяет версию рантайма при импорте.

## 7. stand_core: настройки, логи, ошибки, клиенты

- `Settings` наследует `BaseSettings` и `nuke_di.Client` одновременно и объявляет `__init__(self) -> None`: иначе mypy синтезирует `__init__` из полей, и плагин nuke-di считает каждое поле зависимостью-клиентом. Подклассы настроек в сервисах делают так же. Конфликт pydantic-хуков `__get_pydantic_*_schema__` у двух баз снят явным переопределением со стандартным поведением pydantic. `.env` pydantic-settings не читает — переменные приходят из окружения контейнера. `env_file` в compose нет: каждая переменная передаётся явно в блоке `environment:` как `${VAR:-default}`, а `.env` служит только для подстановки этих значений. Переменная, которой нет в `environment:` сервиса, в контейнер не попадает, даже если она есть в `.env`.
- Адреса (`POSTGRES_DSN`, `REDIS_URL`) не имеют значений по умолчанию и необязательны в `Settings`: сервис без Postgres/Redis не обязан их задавать. `Postgres` и `Redis` падают с понятной ошибкой в `connect()`, если адреса нет. `STAND_API_KEY` обязателен.
- `Postgres.apply_schema(path)` выполняет `schema.sql` целиком; вызывает его `connect()` репозитория сервиса (репозиторий зависит от `Postgres` и подключается после него).
- `Redis` работает с `decode_responses=True`: ключи и значения — `str`.
- Маскировка в логах — по именам ключей (`password`, `*_token`, `authorization`, `x-api-key`, `code`, ...) на любой глубине, плюс `Bearer <token>` в строках. Ключ `code` маскируется всегда (это код подтверждения), поэтому статус вызова логируется под ключом `status`.
- `build_status()` переводит доменное исключение в `grpc.Status` с `google.rpc.Status` в `grpc-status-details-bin`; у любого другого исключения — `INTERNAL` с текстом `Internal error`, без текста и стека исключения. `ERROR_DOMAIN` для `ErrorInfo` — `stand.local`. `DependencyUnavailable` — `ErrorInfo(reason="DEPENDENCY_UNAVAILABLE", metadata={"dependency": ...})`.
- ruff: `RUF001`–`RUF003` выключены — докстринги и комментарии на русском. mypy: `googleapis-common-protos` поставляет `.pyi` без `py.typed`, для `google.rpc.*` включён `follow_untyped_imports`; стабы `asyncpg-stubs` и `types-grpcio-status` — в dev-группе.

## 8. stand_core: декоратор rpc, grpc_server, связка с nuke-di

- `rpc` требует, чтобы первые два аргумента назывались именно `request` и `context` и были позиционными; оба с type hints, плюс аннотация возврата. Исходящий стрим — `AsyncIterator[Resp]` (принимается и `AsyncGenerator[Resp, None]`), и такой хэндлер обязан быть async-генератором; unary — `async def`. Повторная регистрация того же метода другой функцией — `ValueError` (повторное декорирование той же функции — не ошибка).
- `grpc_server(handlers, interceptors, *, port=None, grace=None, host="[::]")` отдаёт `RunningServer(server, port, services)`. `port` по умолчанию — env `GRPC_PORT` (0 — свободный порт, для тестов), `grace` — `SHUTDOWN_GRACE_SECONDS - 1`, чтобы `server.stop(grace)` гарантированно уложился в общий таймаут остановки. Env читается напрямую, а не через `Settings`: серверу не нужен `STAND_API_KEY`, и `grpc_server` остаётся вызываемым без контейнера.
- Сверка с proto собирает все расхождения в одну `ProtoMismatchError(ValueError)` до создания сервера. Методы сервиса без хэндлера — одно warning-событие `grpc.unimplemented_methods` на сервис; UNIMPLEMENTED отвечает сам grpc (generic handler не знает метода).
- Health: общий статус `""` — `NOT_SERVING` до `start()`, затем `SERVING` вместе с каждым сервисом; перед `stop(grace)` — `enter_graceful_shutdown()` (всё `NOT_SERVING`). Reflection отдаёт сервисы хэндлеров, `grpc.health.v1.Health` и сам reflection.
- Graceful stop — только при нормальном выходе из блока (`shutdown.wait()` вернулся); при исключении в блоке сразу `stop(None)` в `finally`.
- `resolve_interceptors()` без аргументов резолвит `DEFAULT_INTERCEPTORS` (раздел 9); можно передать свой список. `inject_handlers` возвращает копию реестра, `GRPC_HANDLERS` не меняется.
- Healthcheck для compose — `python -m stand_core.grpc.healthcheck [--addr] [--service] [--timeout]`. Вызов `Check` идёт через `channel.unary_unary`, а не `HealthStub`: в `types-grpcio-health-checking` у стаба нет методов, а `type: ignore` вне gen/ не используем. В dev-группе добавлены `types-grpcio-health-checking` и `types-grpcio-reflection`.
- Процесс `@worker`, остановленный SIGTERM, завершается кодом 143 (128 + сигнал) — так nuke-di сообщает об остановке по сигналу, это не ошибка.
- Тесты stand_core изолируют глобальный `GRPC_HANDLERS` и сбрасывают structlog после каждого теста (conftest). Шаблон `main.py` проверяется end-to-end: `tests/example_main.py` запускается отдельным процессом, отвечает на вызов с внедрённым клиентом и останавливается по SIGTERM.

## 9. stand_core: интерцепторы и базовый клиент к соседям

- Все пять интерцепторов — настоящие `grpc.aio.ServerInterceptor` (и nuke-di `Client`), обёртка хэндлера в `grpc_server` не понадобилась. Общая база `CallInterceptor` подменяет behavior `RpcMethodHandler` любого из четырёх типов: каждый вызов выполняется внутри `around(call)` — async context manager'а, который видит `context`, исключения хэндлера и счётчики сообщений (`received` для входящих стримов, `sent` для исходящих). Публичный API `rpc` не менялся.
- Порядок — `DEFAULT_INTERCEPTORS`: RequestId → Logging → Auth → StreamCount → ExceptionHandling (первый — самый внешний). Поэтому Logging видит уже готовый статус (после `abort`, через `context.code()`), а AuthInterceptor, который стоит снаружи ExceptionHandling, сам вызывает `abort_with_error`.
- Health и reflection (`/grpc.health.v1.Health/`, `/grpc.reflection.`) интерцепторы стенда не трогают вовсе: им не нужен `x-api-key`, а healthcheck compose не засоряет логи строкой на каждый probe. Такие вызовы идут без `x-request-id`.
- grpc.aio запускает каждый вызов в отдельной задаче, поэтому contextvars (`request_id`, `current_user`, `authorization`, deadline) не протекают между вызовами; интерцепторы всё равно сбрасывают их по выходе.
- `context.abort(code, details, trailing_metadata)` заменяет уже выставленную trailing metadata, а `set_trailing_metadata` после abort игнорируется. Поэтому `abort_with_error` склеивает текущую trailing metadata с `grpc-status-details-bin`, а `x-items-count` выставляется только при успешном завершении стрима (к trailing metadata хэндлера, например `x-close-reason`, добавляется, а не заменяет её). Trailing metadata в `abort` — только tuple, список grpc отвергает с `TypeError`.
- ExceptionHandling пропускает `grpc.aio.AbortError` как есть (хэндлер сам вызвал `context.abort`, антипример `LegacyResetPassword`), доменное исключение → статус + details, прочее → `INTERNAL: Internal error` и событие `grpc.unhandled_exception` со стеком в лог. `asyncio.CancelledError` не перехватывается.
- Logging: событие `grpc.call` с `method`, `grpc_type`, `request_id`, `status`, `duration_ms`, для стримов — `messages_received` / `messages_sent`; `info` для `OK`, `warning` для остальных статусов. Тела запросов не логируются. RequestId дополнительно привязывает `request_id` к structlog contextvars, так что его несут и логи хэндлеров.
- Таблица политик — глобальный реестр `AUTH_POLICIES` (полное имя метода → `service`/`user`/`seller`), сервис заполняет его через `register_auth_policies` рядом с регистрацией хэндлеров, как `GRPC_HANDLERS`. Метод без строки в таблице требует пользователя (`user`): забытая политика не открывает метод. `x-api-key` сравнивается через `hmac.compare_digest`.
- Сессии: `Sessions(Client)` поверх `Redis`, ключ `session:{token}`, значение — JSON `{"user_id", "role"}` с TTL. Пишет user-service, читает AuthInterceptor; битое значение = нет сессии (`UNAUTHENTICATED`). Неизвестная роль — тоже битая сессия.
- Для исходящих вызовов AuthInterceptor кладёт в contextvar исходный заголовок `authorization` пользователя, а RequestIdInterceptor — deadline входящего вызова (`time.monotonic() + context.time_remaining()`); без deadline `time_remaining()` в grpc.aio — `None`.
- `GrpcClient(Client)` — базовый клиент к соседям: подкласс задаёт `address_env` (`CATALOG_ADDR`, `ORDERS_ADDR`) и `dependency`. Адрес читается из env в `connect()` напрямую, а не через `Settings`: у каждого клиента своя переменная, и `Settings` не разрастается адресами всех соседей. Канал ленивый — сосед может подняться позже. Каждый вызов несёт `x-api-key`, `x-request-id` текущего вызова и, если `forward_authorization=True`, `authorization` пользователя; deadline — остаток входящего, иначе `GRPC_DEFAULT_DEADLINE_SECONDS`, или явный `deadline=` (имя не `timeout`: ruff ASYNC109). `UNAVAILABLE`/`DEADLINE_EXCEEDED` → `DependencyUnavailable(dependency)`, прочие статусы остаются `AioRpcError` — их разбирает сервис (например, `FAILED_PRECONDITION` с деталями от catalog в Checkout).
- Шаблон `main.py` в тестах (`tests/example_main.py`) резолвит интерцепторы без `AuthInterceptor`: тест идёт без Redis. В сервисах — `resolve_interceptors()` со всеми пятью.
- В тестах rich details читаются из `grpc-status-details-bin` хелпером `stand_core.testing.rich_status` (общий для тестов всех сервисов): `rpc_status.from_call` в `types-grpcio-status` типизирован под `grpc.Call`, а не `grpc.aio.AioRpcError`.

## 10. catalog-service: CatalogService v1/v2

- Пакет `services/catalog` (`catalog-service`, модуль `catalog_service`): `settings.py` (`CatalogSettings(Settings)` с `IMPORT_MAX_ROWS`), `models.py` (доменные `Product`, `ProductFilter`, `ImportItem` — репозиторий и хэндлеры не зависят от версии proto), `repository.py` (`CatalogRepository(Client)` поверх `Postgres`, применяет `schema.sql` в `connect()`), `convert.py` (Product → v1/v2, копейки ↔ `Money`), `search.py` (пагинация и общая часть поиска v1/v2), `auth.py` (таблица политик), `handlers/` — один хэндлер на файл. v2-хэндлеры — `v2_*_u_u.py`, функции `get_product_v2` / `search_products_v2`.
- Каждый сервис добавляет свой `src/` в `mypy_path` корневого `pyproject.toml`, иначе mypy видит модуль под двумя именами.
- Схема `catalog`: `products` (`product_id text` = `gen_random_uuid()::text`, уникальность `(seller_id, offer_id)`, цена в копейках), `stocks` (остаток на складе), `reservations` (`(order_id, product_id)` → количество, для StockService). Доступный остаток = остаток − резервы, не меньше нуля; это и есть `Product.stock` в ответах. `product_id` — text, а не uuid: произвольная строка в `GetProduct` даёт `NOT_FOUND`, а не ошибку приведения типа.
- Продавец-сид `seller@stand.local` имеет фиксированный id `00000000-0000-4000-8000-000000000001`: catalog сидирует его товары (24 штуки в 4 категориях: electronics, books, home, sport; один — с нулевым остатком), user-service создаст продавца с тем же id. Сиды идемпотентны (`ON CONFLICT DO NOTHING`): перезапуск не затирает правки курса, `make reset` возвращает исходные.
- Пагинация: `page_token` — base64url от JSON `{"offset": N}`; битый токен, не-int или отрицательный offset → `INVALID_ARGUMENT` + `BadRequest(pagination.page_token)`. `page_size`: 0 → 20, больше 100 → 100, отрицательный → `INVALID_ARGUMENT`. Следующая страница определяется запросом `limit + 1` записи. Токены v1 и v2 совместимы. Offset, а не keyset, — проще и достаточно для учебного каталога.
- Поиск: подстрока в названии без учёта регистра (`strpos(lower(...))`, без экранирования `%`/`_`), категория — точное совпадение, цена включительно; `min > max` и отрицательные цены → `INVALID_ARGUMENT`. Сортировка по умолчанию — по названию; при равенстве — по `product_id`, чтобы страницы были стабильны. Неизвестное значение enum сортировки — сортировка по умолчанию.
- `GetProduct` с пустым `product_id` → `INVALID_ARGUMENT` (а не `NOT_FOUND`).
- catalog.v2: `region_id` обязателен (пустой или из пробелов → `INVALID_ARGUMENT`), на выдачу пока не влияет — регионов в данных нет. `Money` — только `RUB` (пустой `currency_code` тоже считается рублями), неотрицательная, с точностью до копейки (`nanos` кратны 10⁷); нарушения → `INVALID_ARGUMENT` с полем (`min_price.currency_code`, `max_price.nanos`, ...).
- ImportProducts: сначала читается и проверяется весь стрим, затем валидные строки пишутся **одной транзакцией**. Поэтому стрим длиннее `IMPORT_MAX_ROWS` отклоняется целиком (`RESOURCE_EXHAUSTED` + `QuotaFailure(subject="seller:<id>")`) без частично применённого импорта; 10 000 строк в памяти — немного. Режим `IMPORT_MODE_UNSPECIFIED`, второй заголовок, стрим без заголовка (в т.ч. пустой, или первое сообщение без payload) → `INVALID_ARGUMENT`. Проверки строки: `offer_id`, `name`, `category` не пустые (пробелы по краям обрезаются) и не длиннее 64/255/64 символов, `price_kopecks > 0`, `stock >= 0`. У строки может быть несколько ошибок; `failed` — число строк с ошибками, `errors` — по одной записи на поле, по возрастанию номера строки. В `CREATE_ONLY` существующий `offer_id` (в том числе повтор внутри того же фида) — ошибка строки по полю `offer_id`. Импорт задаёт остаток на складе (`stocks.quantity`), резервы не трогает.
- ExportProducts: keyset-пачки по `EXPORT_BATCH = 100` строк (`(updated_at, product_id) > (последняя строка пачки)`), порядок — `updated_at, product_id`; `updated_since` включительно. Каждая пачка — отдельный короткий `pool.fetch`, между `yield` соединение не занято: клиент, который перестал читать стрим (flow control HTTP/2 блокирует `yield`), иначе держал бы соединение и транзакцию, а пять таких стримов исчерпали бы пул из 5 соединений — и встали бы ReserveStock/ReleaseStock. Цена — нет единого снимка: товар, изменённый во время выгрузки, может попасть в неё повторно с новым `updated_at`. Хэндлер закрывает генератор через `aclosing`; перед каждой отправкой проверяется `context.done()`.
- Тесты: хэндлеры вызываются напрямую с `FakeRepository` (репозиторий в памяти, подкласс `CatalogRepository`) и `Mock`-контекстом; `test_server.py` поднимает сервис in-process со всеми интерцепторами (сессии подменены) и проверяет статусы и details по сети; `test_wiring.py` импортирует настоящий `main.py` в подпроцессе и проверяет дерево клиентов; `test_repository.py` проверяет SQL против Postgres из compose во временной базе (`TEST_POSTGRES_DSN`, по умолчанию `localhost:5432`) и пропускается, если Postgres недоступен.
- Хелпер `rich_status` переехал из тестов stand_core в `stand_core.testing`, чтобы тесты сервисов не копировали его.
- compose: общие якоря `x-python-service` (образ, сборка, `mem_limit: 128m`), `x-common-env` (общие переменные с дефолтами из `.env.example`, так что `make up` работает и без `.env`) и `x-grpc-healthcheck`. catalog зависит от Postgres и Redis (Redis нужен AuthInterceptor для сессий). Дефолт `IMPORT_MAX_ROWS` в `.env.example` исправлен на 10 000, как в ТЗ.

## 11. catalog-service: StockService

- Доменные `StockItem`, `StockShortage`, `ReserveResult` в `models.py`; репозиторий возвращает нехватку как данные, а `FailedPrecondition` собирает хэндлер.
- ReserveStock — одна транзакция: `pg_advisory_xact_lock(hashtext(order_id))` (повторы одного заказа строго по очереди), затем проверка существующего резерва, затем `SELECT ... FOR UPDATE OF p` строк товаров в порядке `product_id` (параллельные резервы одних товаров не перепродают остаток и не ловят deadlock). Нехватка хотя бы одной позиции — ничего не пишется.
- Идемпотентность: если под `order_id` уже есть резерв, он возвращается как есть, без проверки остатков и без сравнения с запрошенными позициями. Резерв хранится строками `reservations`; `ReleaseStock` их удаляет (`released=false`, если строк уже не было). Поэтому `ReserveStock` после `ReleaseStock` с тем же `order_id` резервирует заново — order-service так не делает, а отдельная таблица статусов резервов была бы лишней.
- Нехватка → `FAILED_PRECONDITION` + `PreconditionFailure`, по нарушению на товар: `type=INSUFFICIENT_STOCK` (description `requested N, available M`) или `PRODUCT_NOT_FOUND` для несуществующего товара, `subject=product:<id>`. Неизвестный товар — тоже `FAILED_PRECONDITION`, а не `NOT_FOUND`: Checkout по ТЗ отдаёт «нет товара» как `FAILED_PRECONDITION` с деталями от catalog.
- Валидация ReserveStock: пустой `order_id`, пустой список, пустой `product_id`, `quantity <= 0`, повтор товара в запросе → `INVALID_ARGUMENT` + `BadRequest` (`items[i].quantity`, ...). Повторы не складываются — так проще и явно.
- Задержка: metadata `x-debug-delay-ms` переопределяет env `STOCK_RESERVE_DELAY_MS` для одного вызова (в том числе `0` отключает задержку из env); не целое или отрицательное значение → `INVALID_ARGUMENT` с полем `x-debug-delay-ms`. Задержка — до резерва и не дольше deadline вызова: если deadline короче, сервер ждёт только до него и завершает вызов `DEADLINE_EXCEEDED` без резерва (клиент всё равно уже получил ошибку и о резерве бы не узнал). Верхнего предела у задержки нет.
- GetStock: пустой `product_id` → `INVALID_ARGUMENT`, нет товара → `NOT_FOUND` + `ResourceInfo`.
- `metadata_value` (чтение заголовка из invocation metadata) теперь экспортируется из `stand_core.grpc`.

## 12. user-service

- Пакет `services/users` (`user-service`, модуль `user_service`): `settings.py` (`UserSettings`: `SESSION_TTL_S`, `CONFIRM_CODE_TTL_S`, `SEED_SELLER_PASSWORD`), `models.py`, `repository.py` (`UserRepository(Client)` поверх `Postgres`), `confirm_codes.py` (`ConfirmCodes(Client)` поверх `Redis`), `passwords.py`, `validation.py`, `convert.py`, `auth.py`, `handlers/`. Сессии пишет общий `stand_core.clients.Sessions` — тот же, что читает AuthInterceptor.
- Схема `users.users`: `user_id text` (`gen_random_uuid()::text`), `email` уникален, `role` — `BUYER`/`SELLER`, `status` — `PENDING`/`ACTIVE`. Email нормализуется (обрезка пробелов, нижний регистр) во всех методах, в базе хранится нормализованным.
- Пароли — `hashlib.scrypt` (n=2¹⁴, r=8, p=1, соль 16 байт, ~16 МБ памяти на хэш), формат `scrypt$n$r$p$salt$hash` с параметрами внутри хэша; хэширование и проверка — в отдельном пуле из 2 потоков (`MAX_PARALLEL_HASHES`), чтобы не блокировать event loop и не выйти за `mem_limit` при всплеске входов (§22). Сравнение — `hmac.compare_digest`.
- Сид `seller@stand.local` (id `00000000-0000-4000-8000-000000000001`, как у товаров-сидов catalog, роль SELLER, подтверждён) пишет `UserRepository.connect()`, а не `schema.sql`: хэш пароля из env в SQL не посчитать. Вставка `ON CONFLICT DO NOTHING` и только если сида ещё нет — перезапуск не затирает смену пароля, `make reset` возвращает исходный. У `SEED_SELLER_PASSWORD` есть дефолт (`seller-password`, как в `.env.example`).
- Валидация SignUp (все нарушения сразу, `BadRequest`): email — намеренно простая проверка (одна `@`, точка в домене, без пробелов, ≤ 254), пароль ≥ 8 символов, `display_name` не пустой после обрезки и ≤ 100, `role` — `UNSPECIFIED` = BUYER, неизвестное значение enum → нарушение поля `role`. Регистрация продавца через SignUp разрешена (proto это допускает).
- Код подтверждения — 6 цифр (`secrets.randbelow`), `confirm:{email}` с TTL `CONFIRM_CODE_TTL_S` (900 с). Повторного SignUp для PENDING-пользователя нет (`ALREADY_EXISTS`): если код истёк, курс делает `make reset` или регистрирует другой email.
- ConfirmEmail, порядок проверок: пустые поля → `INVALID_ARGUMENT`; нет пользователя → `NOT_FOUND` (`ResourceInfo` user); уже ACTIVE → `FAILED_PRECONDITION` (`EMAIL_ALREADY_CONFIRMED`); кода нет в Redis (истёк) → `NOT_FOUND` (`ResourceInfo` confirmation_code); код не совпал → `INVALID_ARGUMENT` (`BadRequest` по `code`). После подтверждения код удаляется.
- SignIn: нет пользователя и неверный пароль — один и тот же `UNAUTHENTICATED: Invalid email or password` (не выдаём занятые email). Пароль проверяется раньше статуса: `FAILED_PRECONDITION` (`EMAIL_NOT_CONFIRMED`) видит только тот, кто знает пароль. Токен — `secrets.token_urlsafe(32)`, каждый вход — новая сессия, `expires_at` = сейчас + `SESSION_TTL_S`.
- SignOut удаляет только текущую сессию (токен из `authorization` вызова); другие сессии пользователя живут до TTL. GetMe для сессии удалённого пользователя → `NOT_FOUND`.
- UpdateProfile: пустая маска → `INVALID_ARGUMENT` (`update_mask`), а не «обновить всё»: так случайно не стирается телефон. Неизвестный путь → `INVALID_ARGUMENT` с полем `update_mask.paths[i]`. Поля вне маски не меняются, даже если заданы в `profile`. `phone` в маске без значения (или пустой) удаляет телефон. Телефон — 5–15 цифр с необязательным `+`.
- LegacyResetPassword (антипример, комментарий в хэндлере): невалидный email, короткий пароль и неизвестный пользователь — всё `context.abort(UNKNOWN, "Validation failed")` без details. Сессии пользователя при смене пароля не сбрасываются (индекса сессий по пользователю нет).
- Тесты: хэндлеры вызываются напрямую с репозиторием, кодами и сессиями в памяти (`tests/fakes.py`); `test_server.py` — сервис in-process со всеми интерцепторами (сценарий SignUp → ConfirmEmail → SignIn → GetMe → UpdateProfile → SignOut, details по сети, UNKNOWN без `grpc-status-details-bin`); `test_repository.py` — SQL и сид против Postgres из compose, пропускается без него. `UserServiceAsyncStub` есть только в `.pyi`, поэтому в тестах он в строковых аннотациях.

## 13. order-service: корзина, Checkout, заказы

- Пакет `services/orders` (`order-service`, модуль `order_service`): `settings.py` (`OrderSettings`: `IDEMPOTENCY_TTL_S`), `models.py` (`Order`, `OrderItem`, `OrderStatus`), `repository.py` (`OrderRepository(Client)` поверх `Postgres`), `carts.py` (`Carts(Client)`) и `idempotency.py` (`IdempotencyKeys(Client)`) поверх `Redis`, `catalog_client.py` (`CatalogClient`) и `stock_client.py` (`StockClient`) — два клиента на базовом `GrpcClient`, оба с адресом из `CATALOG_ADDR`, `cart_view.py` (корзина с ценами для ответа), `pagination.py` (копия правил catalog), `convert.py`, `auth.py`, `handlers/`.
- Схема `orders`: `orders` (`order_id text` — uuid, который выбирает order-service; он же `order_id` резерва в catalog) и `order_items` (позиция по порядку корзины, снимок названия и цены на момент оформления). Сумма заказа не хранится — считается из позиций.
- Корзина — hash `cart:{user_id}`: product_id → количество, `AddCartItem` прибавляет (`HINCRBY`). Пустой `product_id` или `quantity <= 0` → `INVALID_ARGUMENT`; товара нет в catalog → `NOT_FOUND` (`ResourceInfo` product). Остаток при добавлении не проверяется — его сверяет резерв в Checkout, а `available` в корзине показывает, сколько есть. `RemoveCartItem` для позиции, которой нет в корзине, → `NOT_FOUND` (`ResourceInfo` cart_item). `GetCart` берёт название, цену и остаток через `GetProduct` (параллельно, по запросу на товар); товары, которых уже нет в catalog, в ответ не попадают (и из Redis не удаляются), чтобы корзина не ломалась целиком.
- Деньги: копейки из catalog.v1 → `Money` RUB (`units` + `nanos`), как в catalog.v2.
- Checkout, порядок: `idempotency-key` (пустой, из пробелов или длиннее 128 → `INVALID_ARGUMENT` с полем `idempotency-key`) → повтор с тем же ключом возвращает тот же заказ (в текущем статусе, даже если корзина с тех пор изменилась) → пустая корзина → `FAILED_PRECONDITION` (`CART_EMPTY`) → `ReserveStock` → снимок цен через `GetProduct` → заказ `CREATED` → ключ фиксируется → корзина очищается целиком.
- Идемпотентность: ключ `idem:{user_id}:{key}` сначала занимается значением `pending:{order_id}` (`SET NX`, TTL 30 с), после создания заказа перезаписывается на `order_id` с TTL `IDEMPOTENCY_TTL_S` (сутки). Параллельный повтор, пока первый вызов идёт, → `FAILED_PRECONDITION` (`CHECKOUT_IN_PROGRESS`). Короткий TTL у `pending` — чтобы оборванный вызов (отмена клиентом, deadline) не блокировал ключ на сутки. При любой ошибке Checkout ключ удаляется: повтор с тем же ключом оформляет заказ заново. Если по ключу нет заказа (база очищена, Redis нет), ключ забывается и заказ оформляется заново.
- Ошибки catalog: `FAILED_PRECONDITION` от `ReserveStock` превращается в `FailedPrecondition` с теми же нарушениями `PreconditionFailure` (по товарам, `INSUFFICIENT_STOCK` / `PRODUCT_NOT_FOUND`) и сообщением catalog — клиент получает детали catalog как есть. Для этого в stand_core добавлены `error_status` (google.rpc.Status из `AioRpcError`) и `precondition_violations`; `stand_core.testing.rich_status` построен на `error_status`. `UNAVAILABLE` / `DEADLINE_EXCEEDED` от catalog → `DependencyUnavailable` → `UNAVAILABLE` + `ErrorInfo(DEPENDENCY_UNAVAILABLE, dependency=catalog)`, заказ не создаётся.
- Если резерв мог состояться, а заказ не создан (таймаут ответа catalog, ошибка после резерва, товар пропал между резервом и `GetProduct`), резерв снимается «тихо»: `ReleaseStock` со своим deadline 1 с (deadline входящего вызова к этому моменту может истечь), ошибки — только в лог.
- deadline: исходящие вызовы к catalog получают остаток deadline входящего вызова (базовый клиент). Поэтому, если клиент сам задал deadline, при остановленном или медленном catalog он увидит свой `DEADLINE_EXCEEDED` (сработает раньше ответа order-service); без deadline у клиента order-service ответит `UNAVAILABLE` через `GRPC_DEFAULT_DEADLINE_SECONDS` (5 с) — не висит. Проверено на поднятом стенде с остановленным catalog.
- GetOrder / CancelOrder: чужой и несуществующий заказ неразличимы — `NOT_FOUND` (`ResourceInfo` order); пустой `order_id` → `INVALID_ARGUMENT`.
- ListOrders: новые первыми (`created_at DESC, order_id DESC`), пагинация как в catalog (offset-токен), `status` не задан или `UNSPECIFIED` — все статусы, неизвестное значение enum → `INVALID_ARGUMENT`.
- CancelOrder: отмена — условный `UPDATE ... WHERE status IN (CREATED, PAID, ASSEMBLING)`, поэтому не обгоняет смену статуса доставкой; иначе `FAILED_PRECONDITION` (`ORDER_NOT_CANCELLABLE`, в описании — текущий статус). После отмены — `ReleaseStock`. Повторная отмена уже отменённого заказа — не ошибка: она снова вызывает `ReleaseStock` (идемпотентен) и возвращает заказ. Так повтор после `UNAVAILABLE` от catalog доводит снятие резерва до конца.
- compose: orders зависит от Postgres, Redis и catalog (`service_healthy` — только порядок старта; остановленный позже catalog даёт `UNAVAILABLE`), `CATALOG_ADDR` по умолчанию `catalog:50052`.
- Тесты: хэндлеры вызываются напрямую с фейками в памяти (`tests/fakes.py`: репозиторий, корзины, ключи, `FakeStock`, `FakeCatalog`); `test_server.py` — сервис in-process со всеми интерцепторами, `StockClient` и `CatalogClient` подменены через `Dependencies.override`; `test_clients.py` — настоящие клиенты против поддельного catalog-service in-process (`tests/neighbour.py`), в том числе Checkout по сети с проверкой проброса deadline и `x-request-id` в `ReserveStock`; `test_repository.py` — SQL против Postgres из compose (пропускается без него); `test_wiring.py` — дерево клиентов из настоящего `main.py`.

## 14. order-service: имитация доставки и TrackOrder

- Доставка — `Fulfillment(Client)` (`fulfillment.py`): asyncio-таск, который `serve` в `main.py` запускает через `BackgroundTasks` из nuke-di (тот отменяет таск при остановке и пишет в лог, если таск упал). Отдельный `@worker` не нужен: процесс один, а таск живёт ровно столько, сколько сервер.
- Состояние доставки — только в Postgres: заказ уходит на следующий статус, когда простоял в текущем `FULFILLMENT_STEP_MS` (по `updated_at`, часы Postgres). Один проход — один условный `UPDATE ... SET status = CASE ... WHERE status IN (CREATED, PAID, ASSEMBLING, HANDED_TO_COURIER) AND updated_at <= now() - step RETURNING`. Поэтому рестарт сервиса продолжает доставку с того же места, вторая реплика не продвинет заказ дважды (условие перепроверяется под блокировкой строки), а `CancelOrder` (тоже условный `UPDATE`) и доставка не обгоняют друг друга. Отменённые и доставленные заказы под условие не попадают. Для прохода — частичный индекс по `updated_at` только у заказов в доставке.
- Опрос — раз в `min(шаг, 0.5 с)`: смена статуса запаздывает не больше чем на полсекунды. Ошибка прохода (Postgres недоступен) пишется в лог, следующий проход идёт по расписанию.
- `FULFILLMENT_STEP_MS` по умолчанию 2000, как в ТЗ (в `.env.example` и compose — тоже 2000).
- Каждая смена (доставка и `CancelOrder`) публикуется в Redis `orders.status.{order_id}` JSON-ом `{order_id, status, changed_at}` после записи в Postgres. Ошибка публикации — только warning в логе: статус уже в Postgres, а `TrackOrder` его перечитает (см. ниже).
- `TrackOrder`: сначала проверка заказа (пустой `order_id` → `INVALID_ARGUMENT`, чужой или нет → `NOT_FOUND`, как у `GetOrder`, без подписки в Redis), затем подписка, затем текущий статус из Postgres первым сообщением. Подписка считается действующей после подтверждения `SUBSCRIBE` от Redis, поэтому смена между подпиской и чтением не теряется: она придёт событием. Событие, уже учтённое в прочитанном статусе, отбрасывается по `changed_at` (`changed_at` = `updated_at` заказа): клиент не получает статус дважды. Стрим закрывается `OK` после `DELIVERED` или `CANCELLED`; `x-items-count` ставит `StreamCountInterceptor`.
- Если 10 с не было событий, `TrackOrder` перечитывает статус из Postgres: так потерянная публикация (Redis моргнул) не подвешивает стрим до конца deadline.
- Каждый `TrackOrder` держит своё соединение с Redis (pub/sub); выход из стрима, в том числе отмена клиентом, возвращает его в пул (`async with pubsub`). Проверено на поднятом стенде: после стримов подписчиков в Redis не остаётся.
- Тесты: `test_fulfillment.py` (шаги до `DELIVERED` при шаге 10 мс, отменённые стоят, ошибка публикации и прохода не останавливает доставку), `test_track_order.py` (хэндлер напрямую с `FakeEvents` — pub/sub в памяти: текущий статус первым, смена между подпиской и чтением не теряется и не дублируется, закрытие на финальном статусе и на событии отмены, перечитывание без событий, `NOT_FOUND`), `test_server.py` (по сети, `x-items-count`), `test_repository.py` (`advance_due` против Postgres), `test_events.py` (`OrderEvents` против Redis из compose, без него пропускается).

## 15. support-service: Chat и GetChatHistory

- Чат — один на заказ (`support.chats`, `order_id UNIQUE`), создаётся при первом успешном `join` и принадлежит владельцу заказа. Сообщения — `support.messages`; порядок задаёт identity-колонка `seq`, а не `created_at`: у двух быстрых сообщений время может совпасть. Сохраняются все сообщения: покупателя (с `client_message_id`), оператора и бота. `read{message_id}` ставит `read_at` (повторное прочтение его не сдвигает); неизвестное или чужое сообщение — только запись в лог, стрим не рвётся.
- `join` проверяется через `OrdersClient.GetOrder` с `authorization` пользователя и `x-request-id` (базовый клиент stand_core, `forward_authorization=True`): order-service сам отвечает `NOT_FOUND` на чужой заказ, support дополнительно сверяет `user_id`. Нет заказа или он чужой → `NOT_FOUND`; order-service недоступен при `join` → `UNAVAILABLE` (без заказа чат не открыть). Пустой `order_id` → `INVALID_ARGUMENT`.
- Первое сообщение не `join` и стрим, закрытый клиентом до `join`, → `FAILED_PRECONDITION` + `PreconditionFailure(type=JOIN_REQUIRED)`. Повторный `join` в том же стриме → `FAILED_PRECONDITION` (`ALREADY_JOINED`). Пустой текст `message` → `INVALID_ARGUMENT`. Эти ошибки завершают стрим: это ошибки клиента, а не соседа.
- Deadline `GetOrder` — остаток deadline чата, но не больше `GRPC_DEFAULT_DEADLINE_SECONDS`: чат живёт минуты, и его остаток — не срок для одного вызова.
- Независимые потоки: после `joined` у стрима своя `ChatSession` (`chat_hub.py`) с очередью исходящих. Чтение входящих, приветствие оператора и ответы бота — отдельные asyncio-таски, все пишут в эту очередь, хэндлер отдаёт её клиенту. Ошибка любого таска завершает стрим этой ошибкой; при закрытии стрима таски отменяются.
- `ChatHub` (Client-синглтон) — открытые сессии по чатам в процессе: сообщение чата (покупателя — кроме отправителя, он получает `ack`; оператора; бота) получают все стримы этого чата. `agent_typing` и `ack` — только своему стриму. Сессия регистрируется до чтения последних сообщений для `joined`, а сообщения, уже попавшие в `joined`, из очереди не дублируются: между `joined` и стартом сессии ничего не теряется. При нескольких репликах стримы разных реплик друг друга не видят — для учебного стенда (одна реплика) этого достаточно, ТЗ прямо говорит «чат — внутри процесса».
- Приветствие: через `SUPPORT_AGENT_DELAY_MS` после `join` — `agent_typing` и сразу сообщение `AGENT` «Здравствуйте, я оператор поддержки. Чем могу помочь?»; оно сохраняется в историю при каждом `join`.
- Бот: «статус» или «где» в тексте (подстрокой, без учёта регистра) → `GetOrder` в отдельном таске, ответ `BOT` «Заказ {order_id}: {статус по-русски}». `DependencyUnavailable` и прочие ошибки order-service → `BOT` «Не удалось получить статус, попробуйте позже», стрим продолжается.
- Простой: `SUPPORT_IDLE_TIMEOUT_S` (по умолчанию 60, как в ТЗ; в `.env.example` было 300 — исправлено на 60) без входящих сообщений клиента (`message` и `read`; ответы сервера таймер не сбрасывают) → `OK` с trailing metadata `x-close-reason: idle`. До `join` действует тот же таймаут. Клиент закончил писать (half-close) → сервер дожидается ответов бота на уже заданные вопросы и завершает стрим `OK` с `x-close-reason: client_closed`; неотправленное приветствие отменяется. `x-items-count` ставит `StreamCountInterceptor`, как у остальных стримов.
- `GetChatHistory`: история по `order_id`, старые первыми, пагинация как у catalog и orders (`page_size` по умолчанию 20, максимум 100, токен — base64 JSON со смещением, модуль `pagination.py` скопирован, как в order-service). Владелец проверяется по сохранённому чату, без вызова order-service: нет чата или он чужой → `NOT_FOUND` (`ResourceInfo` с типом `chat`), неразличимо.
- compose: support зависит от Postgres (чаты), Redis (сессии в `AuthInterceptor`) и orders (`service_healthy` — только порядок старта), `ORDERS_ADDR` по умолчанию `orders:50053`.
- Тесты: `test_chat.py` — хэндлер напрямую с `FakeRepository`, `FakeOrders` и входящим стримом-очередью (`join` не первым, чужой заказ, приветствие без запроса клиента, ответ бота, недоступный order-service, idle до и после `join`, half-close, `read`, два стрима одного чата); `test_server.py` — по сети со всеми интерцепторами, `OrdersClient` подменён через DI (`x-close-reason`, `x-items-count`, rich details); `test_clients.py` — настоящий `OrdersClient` против поддельного order-service in-process (`tests/neighbour.py`): проброс `authorization` и `x-request-id`, в том числе из чата по сети, ограничение deadline; `test_repository.py` — SQL против Postgres из compose; `test_wiring.py` — дерево клиентов из настоящего `main.py`.

## 16. gateway (BFF)

- FastAPI + `nuke_di.fastapi.setup(app)`: эндпоинты объявлены на `ClientRouter` и получают `UsersClient`, `CatalogClient`, `OrdersClient` по type hint. Клиенты — подклассы базового `GrpcClient` stand_core (адреса `USERS_ADDR`, `CATALOG_ADDR`, `ORDERS_ADDR`), поэтому `x-api-key`, deadline (`GRPC_DEFAULT_DEADLINE_SECONDS`) и перевод `UNAVAILABLE`/`DEADLINE_EXCEEDED` в `DependencyUnavailable` — те же, что у сервисов.
- `authorization` и `x-request-id` HTTP-запроса кладёт в contextvars stand_core ASGI-middleware (`context.py`) — так же, как в сервисах это делают интерцепторы; базовый клиент берёт их оттуда. `x-request-id` из запроса или новый uuid возвращается в заголовке ответа. `authorization` пробрасывается как есть и только в методы Auth: user (`GetMe` и все методы order-service); проверяет его сам сервис, gateway токены не разбирает.
- Запуск — `python -m gateway.main` через `uvicorn.run`, а не `@worker`: контейнер DI подключает lifespan приложения (`setup`), а worker подключал бы его сам, и lifespan отказался бы стартовать на уже подключённом контейнере. Graceful stop по SIGTERM — у uvicorn (`timeout_graceful_shutdown` = `SHUTDOWN_GRACE_SECONDS`).
- Ошибки: `grpc.aio.AioRpcError` сервиса → HTTP-код по канонической таблице google.rpc.Code (`INVALID_ARGUMENT`/`FAILED_PRECONDITION`/`OUT_OF_RANGE` → 400, `UNAUTHENTICATED` → 401 + `WWW-Authenticate: Bearer`, `PERMISSION_DENIED` → 403, `NOT_FOUND` → 404, `ALREADY_EXISTS`/`ABORTED` → 409, `RESOURCE_EXHAUSTED` → 429, `UNAVAILABLE` → 503, `DEADLINE_EXCEEDED` → 504, прочее → 500). Тело: `{"error": {"code", "message", "details"}}`, details — rich details сервиса как JSON с `@type`. Недоступный сервис (и его таймаут) — `DependencyUnavailable` базового клиента → 503 с `ErrorInfo(DEPENDENCY_UNAVAILABLE, dependency=…)`. Ошибки валидации самого HTTP-запроса (тело, неизвестный `status`/`sort`) — стандартные 422 FastAPI, в gRPC они не уходят.
- JSON-ответы — свои pydantic-модели (`schemas.py`), а не `MessageToDict`: int64 остаются числами, enum — короткими именами (`BUYER`, `CREATED`), незаданные `Timestamp`/`phone` — `null`. Цена товара (catalog.v1 `price_kopecks`) отдаётся как `Money` RUB, как в корзине и заказах.
- `/products` — catalog.v1 `SearchProducts` (v2 требует `region_id`, которого у веб-фронта нет): `query`, `category`, `min_price_kopecks`, `max_price_kopecks`, `sort` (`name|price_asc|price_desc|newest`), `page_size`, `page_token`. `/orders` — `status` (`CREATED`…`CANCELLED`), `page_size`, `page_token`.
- `POST /checkout`: заголовок `Idempotency-Key` уходит в metadata `idempotency-key` как есть; без заголовка вызов всё равно идёт в order-service, и тот отвечает `INVALID_ARGUMENT` (400) — проверка ключа в одном месте. Коды ответов: `POST /auth/sign-up` → 201, остальные успешные → 200.
- `GET /healthz` — без вызовов соседей; healthcheck контейнера — `python -m gateway.healthcheck` (urllib на `localhost:$HTTP_PORT/healthz`), без curl в образе. compose: gateway зависит от users, catalog, orders (`service_healthy` — только порядок старта), `mem_limit` 128m (по факту ~50 МБ).
- Тесты: `test_api.py` и `test_errors.py` — `TestClient` с подменой трёх клиентов через `DI.override` (router объявлен на глобальном `DI`, поэтому и подмена в нём); `test_clients.py` — настоящие клиенты через `httpx.ASGITransport` против поддельных users/orders in-process (`tests/neighbour.py`): `x-api-key`, `authorization`, `x-request-id`, `idempotency-key`, rich details по сети, недоступный catalog → 503; `test_wiring.py` — маршруты из настоящего `main.py` и healthcheck. Предупреждение starlette «httpx → httpx2» в `TestClient` отфильтровано в pytest: план тестирует gateway через httpx.

## 17. Smoke-сценарий и память стенда

- `tests/smoke/test_smoke.py` с маркером `stand`: `make test` его пропускает (`addopts = -m 'not stand'`), `make smoke` запускает только его. Тесты ходят с хоста по портам из `.env.example` (`USERS_PORT`…`SUPPORT_PORT`, `STAND_API_KEY`, `SEED_SELLER_PASSWORD`; хост — `STAND_HOST`, Redis — `SMOKE_REDIS_URL`) настоящими gRPC-стабами, без stand_core: так проверяется контракт снаружи, как его увидят тесты курса.
- Каждый прогон регистрирует нового покупателя (`smoke-<uuid>@stand.local`) и импортирует товар с уникальным `offer_id` `SMOKE-<uuid>`, поэтому smoke можно гонять повторно без `make reset`. Для Checkout берётся книга-сид с наибольшим остатком: остатки сидов убывают от прогона к прогону, но их хватает на десятки прогонов.
- Сценарии: покупатель (SignUp → код из Redis `confirm:{email}` → ConfirmEmail → SignIn → SearchProducts → AddCartItem → два Checkout с одним `idempotency-key` дают один заказ → TrackOrder до DELIVERED → Chat: joined, agent_typing и приветствие AGENT без запроса клиента, ack и ответ BOT «доставлен»); продавец-сид (ImportProducts с плохой строкой → `failed=1`, ошибка строки 2 по `price_kopecks` → ExportProducts с `updated_since` содержит импорт); DoD — без `x-api-key` → `UNAUTHENTICATED`, ImportProducts покупателем → `PERMISSION_DENIED`, reflection catalog перечисляет `catalog.v1.CatalogService` и `catalog.v2.CatalogService`. Весь smoke — ~11 с, почти всё время — доставка (4 шага по `FULFILLMENT_STEP_MS`).
- Память (`make stats` сразу после `make up` и smoke, Python 3.12): users ~56 МБ, gateway ~50 МБ, catalog/orders/support ~40 МБ, postgres ~75 МБ, redis ~19 МБ — в сумме ~320 МБ. Сумма `mem_limit` — 960 МБ (5 × 128m + postgres 256m + redis 64m), укладывается в ~1 ГБ; лимиты не меняли.

## 20. Исправления по код-ревью

- Неожиданное (не доменное) исключение при авторизации, например недоступный Redis при чтении сессии, → `INTERNAL: Internal error`, как в ExceptionHandling, а не `UNKNOWN`: AuthInterceptor стоит снаружи ExceptionHandling (§9) и раньше пропускал такие ошибки в grpc. `UNKNOWN` остаётся только у антипримера `LegacyResetPassword`.
- Checkout снимает резерв (§13) и тогда, когда вызов отменён клиентом или истёк его deadline: `ReleaseStock` защищён от отмены (`asyncio.shield`), иначе резерв оставался висеть.
- Недоступный catalog в `GetCart`, `AddCartItem`, `RemoveCartItem` и `Checkout` → `UNAVAILABLE` + `ErrorInfo(DEPENDENCY_UNAVAILABLE, dependency=catalog)`. Раньше параллельные `GetProduct` в `TaskGroup` заворачивали `DependencyUnavailable` в `ExceptionGroup`, и клиент получал `INTERNAL`.
- Offset в `page_token` ограничен сверху: огромный offset → `INVALID_ARGUMENT` «invalid page token» + `BadRequest(pagination.page_token)`, как у битого токена (§10).
- ConfirmEmail без кода в Redis → `NOT_FOUND` с описанием «expired or never issued», без совета «sign up again»: повторный SignUp на уже зарегистрированный email даёт `ALREADY_EXISTS`.
- gateway проверяет диапазоны полей proto (`page_size` ≤ int32, `quantity` и цены в пределах int64): значение вне диапазона → 422, а не 500 из конструктора protobuf. Остальную валидацию (например, `quantity > 0`) по-прежнему делает сервис.

## 21. Исправления по второму код-ревью

- Метка `pending:{order_id}` ключа идемпотентности живёт остаток deadline Checkout плюс 30 с (без deadline — 30 с), а не фиксированные 30 с: медленный резерв (`STOCK_RESERVE_DELAY_MS`) больше не даёт повтору с тем же ключом занять ключ заново и создать второй заказ. `commit` и `forget` — compare-and-set (Lua): меняют ключ, только если в нём всё ещё значение этого вызова, поэтому отстающий вызов не затирает чужую метку или чужой заказ.
- Количество одной позиции корзины ограничено 10 000 (`MAX_CART_QUANTITY`), проверка и `HINCRBY` — одним Lua-скриптом. Раньше огромный `quantity` переполнял `Money.units` или `HINCRBY`, и корзина отвечала `INTERNAL` до удаления позиции.
- `ReleaseStock` берёт тот же advisory-замок по `order_id`, что `ReserveStock`: снятие после таймаута резерва ждёт идущий резерв, а не проходит мимо него, оставляя резерв навсегда.

## 22. Исправления по третьему код-ревью

- Цена товара ограничена 10¹² копеек (`MAX_PRICE_KOPECKS` в `ImportProducts`, `CHECK` в `schema.sql`). Предел количества из §21 сам по себе не держал сумму корзины и заказа в int64: дорогой товар переполнял `Money.units`, и корзина, Checkout, а затем GetOrder/ListOrders по такому заказу отвечали `INTERNAL`. Уже созданная база `CHECK` не получает — `make reset`.
- scrypt (~16 МБ на хэш) считается в пуле из `MAX_PARALLEL_HASHES = 2` потоков вместо общего пула `asyncio.to_thread`: scrypt отпускает GIL, и всплеск SignIn/SignUp выводил user-service за `mem_limit: 128m`.

## 23. Исправления по четвёртому код-ревью

- `ReserveStock` сначала блокирует строки товаров (`FOR UPDATE`), а остатки читает отдельным запросом после блокировки. В READ COMMITTED строки из `LEFT JOIN catalog.stocks` в одном запросе с `FOR UPDATE OF p` оставались из снимка до ожидания замка: UPSERT-импорт, снизивший остаток, не был виден резерву, и тот резервировал больше, чем есть.
- `Money` в фильтрах v2 `SearchProducts` больше предела bigint в копейках → `INVALID_ARGUMENT` (`min_price.units`/`max_price.units`), а не `INTERNAL` от Postgres.
- После создания заказа `commit` ключа идемпотентности и очистка корзины идут под `asyncio.shield`: отмена вызова (ушёл клиент, истёк deadline) не оставляет ключ `pending`, после TTL которого повтор создал бы второй заказ. Потерянный ключ (`commit` вернул False) пишется в лог `orders.idempotency_commit_lost`.

## 24. Исправления по пятому код-ревью

- `ImportProducts` в режиме UPSERT перед записью блокирует уже существующие строки своих `offer_id` (`FOR UPDATE`) в порядке `product_id` — том же, что у `ReserveStock`. Раньше UPSERT брал замки строк в порядке фида, и импорт параллельно с резервом тех же товаров ловил deadlock: Postgres обрывал одну из транзакций, клиент получал `INTERNAL` (откат всего фида или упавший Checkout). Импорты одного продавца идут по очереди под advisory-замком `import:{seller_id}`: два фида с новыми `offer_id` в разном порядке иначе ловили deadlock на уникальном индексе.
