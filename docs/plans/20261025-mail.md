# Почта стенда: RabbitMQ + Mailpit вместо кода из Redis

## Overview

Код подтверждения email сейчас только в Redis (`confirm:{email}`): UI показывает команду
`redis-cli`, smoke читает Redis напрямую. Заменяем это настоящим путём доставки:

```
users-service ──publish (aio-pika)──> RabbitMQ (topic exchange stand.events)
                                          │ routing key user.email_confirmation_requested
                                          ▼
                              notification-service (consumer + SMTP) ──> Mailpit (веб-ящик + API)
                                          │
                                          └──> Postgres: журнал попыток (ListNotifications)
```

Код подтверждения по-прежнему хранится в Redis и сверяется в `ConfirmEmail` — меняется только
доставка. Письма видны в веб-ящике Mailpit, тесты берут их из его REST API.

Новое в стенде: сервисы `rabbitmq` (`rabbitmq:4-alpine`, без management-плагина) и `mailpit`
(`axllent/mailpit`), клиент `Rabbit` в `stand_core`, сервис `services/notifications` (модуль
`notification_service`) с контрактом `notifications.v1`.

Требования меняются осознанно: ограничение C2 ТЗ («только Postgres и Redis») переписывается
закрытым списком «Postgres, Redis, RabbitMQ и Mailpit». C3 (~1 ГБ в покое) остаётся — замер
обновляем.

## Development Approach

- **Testing approach**: Regular (сначала код, потом тесты)
- Каждую задачу доводим до конца, прежде чем браться за следующую
- После каждой задачи: `make check && make test` — зелёные; если задача трогает фронтенд, ещё
  `make front-lint && make front-test`. Коммит `feat: ...` / `fix: ...` / `docs: ...`
- Тесты против живых RabbitMQ/Mailpit пропускаются, если контейнеров нет (как с Postgres и Redis);
  основная проверка — юнит-тесты с фейками в `tests/fakes.py`
- Неочевидные решения записываем в `docs/decisions.md` новым пунктом
- **CRITICAL: every task MUST include new/updated tests**
- **CRITICAL: all tests must pass before starting next task**
